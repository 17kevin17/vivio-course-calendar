# 执行步骤与交接要求

## 推荐执行顺序

### 第1步：建立基线

- 保存当前源码提交。
- 运行现有25个测试并保存输出。
- 保存 Debug APK 的构建结果。
- 记录当前 Room schema/version。

输出：基线提交号、测试结果、已知失败。

### 第2步：修复作息配置

- 将 `schedule_config` 改为复合主键。
- 根据是否已有有效用户数据决定迁移或清库重建。
- 增加 DAO 与约束测试。

完成后单独提交，不与事件身份重构混在一起。

### 第3步：修复兼职 ID 精度

- 检查 POI 实际读取路径。
- 为 ID 列使用无精度损失的字符串读取。
- 对14条样表记录逐字符断言。

### 第4步：引入 identityKey/contentHash

- 修改统一事件模型。
- 编写身份规范化组件。
- 更新两个解析器和测试。
- 保留算法版本号。

### 第5步：重构持久化

- 新增 `managed_event`。
- 新增 `batch_event_action`。
- 将 import_batch 改为状态机。
- 移除旧 event_mapping 承担的多重职责。

### 第6步：重写差异计算

- 先生成纯内存 DiffPlan。
- 明确处理 NEW/UNCHANGED/MODIFIED/CANCELLED/MISSING/AMBIGUOUS/INVALID。
- DiffPlan 在 UI 预览确认后才能执行。

### 第7步：重写执行和撤销

- 先落 PLANNED 操作，再写 CalendarProvider。
- 对每条操作保存 before/after。
- 撤销按动作类型逆操作。
- 实现幂等重试。

### 第8步：故障恢复

- 启动时扫描未完成批次。
- 模拟 Calendar 和 Room 之间的中断点。
- 对无法确定的状态进入人工处理，不自动复制事件。

### 第9步：自动化测试

- 补齐 `05` 中的 P0 用例。
- 生成测试报告。
- 未通过时不得进入功能扩展。

### 第10步：vivo 真机验收

- 使用脱敏样表执行完整流程。
- 记录系统版本、机型、日历版本和测试结果。
- 真机通过后更新项目状态文档。

## 每个任务的交接格式

开发者或下一位代理完成任务时必须提供：

1. 修改文件清单。
2. 数据库 schema 变化。
3. 核心算法变化。
4. 新增测试及运行结果。
5. 尚未验证的行为。
6. 可复现的已知问题。
7. 下一任务建议。

不得只提供“已完成”或测试数量，必须附构建/测试结果和关键断言。

## 下一轮审查需要的材料

- 完整源码仓库或压缩包。
- `git diff` 或提交范围。
- Room schema JSON。
- 单元测试输出。
- Debug/Release 构建输出。
- vivo 真机测试记录；如果尚未执行，明确标注。

仅凭架构总结文档不能证明实现正确。
