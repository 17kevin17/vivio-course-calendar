# 数据库重构方案

## 一、`schedule_config`

同一季节需要保存五个大节，因此必须使用复合主键。

```kotlin
@Entity(
    tableName = "schedule_config",
    primaryKeys = ["season", "periodNumber"]
)
data class ScheduleConfigEntity(
    val season: String,
    val periodNumber: Int,
    val startMinute: Int?,
    val endMinute: Int?,
    val configVersion: Int,
    val updatedAt: Long
)
```

约束：

- `periodNumber` 只能为 1–5。
- 已配置时 `startMinute < endMinute`。
- 同一季节相邻大节不得重叠。
- 春季未确认的下午时段允许为 null，但对应课程必须产生 blocker。

## 二、`managed_event`

这张表表示应用当前管理的逻辑事件，与导入批次解耦。

| 字段 | 作用 |
|---|---|
| id | 本地稳定主键 |
| source | UNIVERSITY / PART_TIME |
| identityKey | 跨批次稳定身份，唯一索引 |
| contentHash | 当前内容哈希 |
| sourceRecordId | 上游稳定 ID，可空 |
| calendarEventId | 当前系统日历事件 ID |
| title/location/description | 当前快照 |
| startMillis/endMillis | 当前时间快照 |
| status | ACTIVE / CANCELLED / MISSING / BROKEN |
| lastSeenBatchId | 最近出现的导入批次 |
| createdAt/updatedAt | 审计时间 |

建议索引：

```text
UNIQUE(source, identityKey)
INDEX(calendarEventId)
INDEX(lastSeenBatchId)
```

## 三、`import_batch`

| 字段 | 作用 |
|---|---|
| id | 批次 ID |
| fileHash/fileName | 文件标识 |
| source/season | 来源和季节 |
| phase | PREPARED / APPLYING / APPLIED / PARTIAL / UNDOING / UNDONE / FAILED |
| createdAt/completedAt | 时间 |
| counts | 各结果统计 |
| errorSummary | 非敏感错误摘要 |

`fileHash` 只能用于判断文件是否完全相同，不能代替事件身份。

## 四、`batch_event_action`

用于恢复和撤销。

| 字段 | 作用 |
|---|---|
| id | 操作 ID |
| batchId | 所属批次 |
| managedEventId | 逻辑事件 ID，可在创建前为空 |
| identityKey | 即使映射未创建也可定位 |
| actionType | CREATE / UPDATE / DELETE / NOOP / MARK_MISSING |
| beforeSnapshot | 操作前 JSON，可空 |
| afterSnapshot | 目标 JSON，可空 |
| calendarEventIdBefore | 操作前系统 ID |
| calendarEventIdAfter | 操作后系统 ID |
| state | PLANNED / CALENDAR_APPLIED / DB_APPLIED / FAILED / REVERTED |
| errorCode | 结构化错误码 |

约束：

```text
UNIQUE(batchId, identityKey)
INDEX(batchId, state)
```

## 五、旧 `event_mapping` 处理

如果当前版本尚未对外发布且没有重要用户数据，优先清库重建，不要为原型数据编写复杂迁移。

如果已经存在需要保留的数据：

1. 为每条旧映射计算临时 identityKey。
2. 相同 source + identityKey 只保留最新有效映射。
3. 写入 `managed_event`。
4. 旧批次只保留统计，不伪造可撤销历史。
5. 明确标记迁移前批次为 `LEGACY_NOT_UNDOABLE`。

不要假装旧数据拥有完整 beforeSnapshot。
