# 导入、更新、撤销与故障恢复

## 一、导入必须采用状态机

CalendarProvider 和 Room 不共享数据库事务，因此不能假设两边同时成功。

建议状态：

```text
PREPARED → APPLYING → APPLIED
                    ↘ PARTIAL
                    ↘ FAILED

APPLIED/PARTIAL → UNDOING → UNDONE
```

## 二、正常导入顺序

1. 解析并生成事件。
2. 计算完整 DiffPlan。
3. 在 Room 创建 `import_batch(PREPARED)`。
4. 将全部 `batch_event_action(PLANNED)` 落库。
5. 批次切换为 `APPLYING`。
6. 逐条执行 CalendarProvider 操作。
7. 每条日历操作成功后记录 `CALENDAR_APPLIED` 和返回 ID。
8. 更新 `managed_event` 后标记 `DB_APPLIED`。
9. 所有操作成功后批次标记 `APPLIED`；部分失败则标记 `PARTIAL`。

关键原则：先记录操作意图，再修改系统日历。

## 三、撤销规则

| 原操作 | 撤销行为 |
|---|---|
| CREATE | 删除创建的系统事件并移除/停用 managed_event |
| UPDATE | 使用 beforeSnapshot 恢复原事件 |
| DELETE | 根据 beforeSnapshot 重建事件，并更新 calendarEventId |
| NOOP | 无操作 |
| MARK_MISSING | 恢复之前的状态标记 |

撤销过程中也必须逐条记录状态，允许再次进入 App 后继续。

## 四、启动恢复

App 启动或进入导入历史页时扫描：

- `APPLYING` 超时批次；
- `UNDOING` 超时批次；
- `CALENDAR_APPLIED` 但未 `DB_APPLIED` 的操作；
- `managed_event` 指向不存在的 calendarEventId；
- 操作日志和长期映射不一致的记录。

恢复策略：

1. 能确认日历操作已完成：补写 Room 状态。
2. 能确认未完成：安全重试。
3. 无法确认：标记 `NEEDS_REVIEW`，不要盲目再创建。

## 五、幂等要求

- 对同一个 `batch_event_action` 重试不能产生第二条日历事件。
- UPDATE 重试只能更新同一 calendarEventId。
- DELETE 目标已经不存在时视为幂等成功，但必须记录事实。
- 相同文件重复导入不能依赖文件哈希直接跳过，仍应验证当前事件映射状态。

## 六、日历事件被用户手动修改

导入前读取当前系统事件并与 `managed_event` 快照比较：

- 未变化：正常执行。
- 用户只修改了非核心字段：提示是否覆盖。
- 用户修改了时间/标题：默认不静默覆盖。
- 系统事件已被删除：允许“重新创建”或“停止管理”。

首版可以把所有外部变化标记为冲突，由用户选择，不需要自动合并。

## 七、提醒机制

- 只使用系统日历 `Reminders` 时，不因本 App 提醒而申请 Android 13 通知权限。
- 如果 App 自己发送“下一节课”通知，再单独申请 `POST_NOTIFICATIONS`。
- 本阶段先验证系统日历提醒，不新增自有提醒服务。

## 八、时区

校内和当前兼职课默认按 `Asia/Shanghai` 解释。时间转换集中在一个组件中，禁止在解析器、数据库和 CalendarWriter 各自转换。
