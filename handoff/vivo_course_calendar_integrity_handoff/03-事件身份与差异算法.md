# 事件身份与差异算法

## 一、两个键必须分离

### `identityKey`

回答：“新旧两条记录是不是同一个逻辑事件？”

它应尽量由稳定字段生成，不能包含希望被识别为修改的字段。

### `contentHash`

回答：“同一逻辑事件的可见内容是否发生改变？”

它应覆盖所有需要同步到系统日历的字段。

## 二、兼职课程

### 稳定身份

首选：

```text
PART_TIME + 原始课节ID
```

原始课节 ID 必须直接读取为字符串。对于 OOXML 数值单元格，优先读取原始 XML 数值或无精度损失的字符串表示，禁止：

```text
getNumericCellValue() → Double → Long → String
```

无课节 ID 时的退化身份只能作为低置信度匹配：

```text
PART_TIME + 规范化学生名 + 规范化课节名称 + 原始开始日期
```

退化匹配发生时间变化时可能存在歧义，必须在预览中标记。

### 内容哈希

包含：标题、学生展示名、状态、开始时间、结束时间、地点、提醒。

## 三、校内课程

校内文件没有真正的上游事件 ID，不能保证所有调课都自动匹配。采用分层匹配：

### 一级：确定性匹配

```text
UNIVERSITY + 学期 + 规范化课程名 + 原始周次 + 原始节次码
```

适合教师或教室变化。

### 二级：候选匹配

当日期或节次发生变化时，按以下字段寻找唯一候选：

- 同一学期；
- 同一规范化课程名；
- 原日期附近；
- 新旧记录在同一导入范围；
- 候选只能有一个。

只在唯一且置信度达到阈值时自动 MODIFIED；否则显示“可能调课”，由用户确认配对。

### 内容哈希

包含：课程标题、教师、教室、日期、开始/结束时间、提醒和状态。

## 四、规范化规则

- Unicode NFKC 规范化。
- 去除首尾空格并合并连续空白。
- 英文字母统一大小写。
- 课程类型标签是否参与 identityKey 必须固定，不可版本间随意变化。
- 不对人名、楼名做模糊拼写纠正。
- 规范化规则需要 `identityVersion`，算法升级时可迁移。

## 五、差异结果

| 条件 | 结果 | 操作 |
|---|---|---|
| 找不到旧 identityKey | NEW | CREATE |
| identityKey 相同且 contentHash 相同 | UNCHANGED | NOOP |
| identityKey 相同且 contentHash 不同 | MODIFIED | UPDATE |
| 上游明确标记取消 | CANCELLED | DELETE 或按产品规则标记 |
| 旧事件本次未出现 | MISSING | 只提示，不自动删除 |
| 多个旧事件都可能匹配 | AMBIGUOUS | 用户确认 |
| 时间或作息缺失 | INVALID | 默认排除 |

## 六、编辑预览后的处理

用户在预览中修改标题、教室或提醒，只改变最终 `contentHash`，不改变已确定的 `identityKey`。

如果用户手动将一个新事件与旧事件配对，应保存这次身份关联，以便后续导入继续识别。
