## 1. 本轮结论与执行原则

当前版本不满足“完整性修复完成”的验收条件。F1 的校内课表身份碰撞已经得到可信修复，取消识别、撤销日志和启动恢复器也已建立基础；但恢复状态机仍存在会造成错误批次状态、孤儿日历事件、错误 `BROKEN` 状态和撤销未完成的缺陷。

下一轮只处理完整性闭环，不扩展新功能。执行时遵守以下原则：

1. CalendarProvider 与 Room 不共享事务，不能用“连续两行代码”假设中间不会中断。
2. 每一个跨存储写入点都必须具备可识别、可重放、可校验的状态。
3. 批次状态必须由动作最终状态汇总得出，禁止恢复函数无条件写成 `APPLIED`。
4. 测试必须覆盖中断边界，不能只验证正常路径和重复调用。
5. 未提交到 GitHub、没有可复现测试产物的内容只能标记为“本地实现待审查”，不能标记为完成。

## 3. 问题定位与修复要求

### R1：`UNDOING` 恢复方向错误

涉及位置：

- `app/src/main/java/com/vivio/coursecalendar/domain/import/ImportManager.kt`
  - `recover()`
  - `undo()`
- `app/src/test/java/com/vivio/coursecalendar/RecoveryTest.kt`
  - `UNDOING批次超时被处理`

现状：

- `recover()` 合并扫描 `APPLYING` 和 `UNDOING`；
- 两种批次使用同一套 CREATE/UPDATE/DELETE 正向恢复分支；
- `DB_APPLIED` 动作直接跳过；
- 最终阶段被写为 `APPLIED` 或 `PARTIAL`；
- 现有测试允许 `UNDOING` 最终成为 `APPLIED`，属于错误断言。

修复要求：

1. 将入口拆分为 `resumeApplying(batch)` 与 `resumeUndoing(batch)`。
2. `resumeUndoing` 按 action 逆序执行，与 `undo()` 共用同一套单动作逆操作函数。
3. `REVERTED` 才允许跳过；`DB_APPLIED` 表示正向动作已完成，正是需要执行逆操作的状态。
4. 全部动作成为 `REVERTED` 后，批次只能进入 `UNDONE`。
5. 任一逆操作失败时，批次进入 `PARTIAL`，保留错误码，不得回写 `APPLIED`。

推荐结构：

```kotlin
private suspend fun resumeApplying(batch: ImportBatchEntity): BatchPhase
private suspend fun resumeUndoing(batch: ImportBatchEntity): BatchPhase
private suspend fun applyAction(...): ActionResult
private suspend fun revertAction(...): ActionResult
private suspend fun summarizeBatchPhase(batchId: Long, direction: Direction): BatchPhase
```

### R2：跨存储 CREATE 缺少幂等标识

涉及位置：

- `BatchEventActionEntity`
- `CalendarGateway`
- `CalendarWriter.insertEvent()`
- `ImportManager.commit()` 的 CREATE 分支
- `ImportManager.undo()` 的 DELETE 逆操作分支
- `ImportManager.recoverCreate()`

危险窗口：

```text
CalendarProvider 插入成功
→ 进程被终止
→ calendarEventId 尚未写回 Room
```

恢复器此时只看到 `PLANNED + calendarEventIdAfter=null`，无法判断系统事件是否已经创建。撤销 DELETE 时也存在同样窗口。

修复要求：

1. `batch_event_action` 增加稳定且唯一的 `operationToken`，在调用 CalendarProvider 前写入。
2. CalendarProvider 事件写入可查询的同步字段，优先使用 Android CalendarContract 支持的同步字段；字段能力必须经过 vivo 真机验证。
3. CalendarGateway 增加按 token 查询接口，例如：

```kotlin
fun findEventByOperationToken(token: String): CalendarEventSnapshot?
```

4. CREATE 或重建前先查 token：
   - 已存在：复用事件 ID并补写 Room；
   - 不存在：执行插入；
   - 查询结果多于一条：停止自动处理并标记人工确认。
5. 若 vivo CalendarProvider 不保留目标字段，必须采用替代可查询标识方案；不能退回“插入后尽快保存 ID”作为完整性保证。

### R3/R4：DELETE 恢复与失败处理不完整

涉及位置：

- `ImportManager.commit()` 的 `BatchActionType.DELETE`
- `ImportManager.recoverDelete()`
- `CalendarGateway.deleteEvent()`

现状：

- 正常 DELETE 忽略 `deleteEvent()` 返回值；
- 恢复时，如果系统事件仍存在，只执行删除并把 action 标成 `DB_APPLIED`；
- 该分支没有同步将 managed 行更新为 `CANCELLED`、清空 `calendarEventId`；
- 删除失败也可能被记录成成功。

修复要求：

1. 调用删除后再次用 `eventExists(cid)` 核验最终状态。
2. 仅当系统事件确认不存在时，执行：

```text
managed_event.status = CANCELLED
managed_event.calendarEventId = null
batch_event_action.state = DB_APPLIED
```

3. 若事件仍存在：
   - action=`FAILED`；
   - errorCode=`CALENDAR_DELETE_NOT_EFFECTIVE`；
   - batch=`PARTIAL`；
   - managed 行保持原状态和原 ID。
4. `calendarEventIdBefore == null` 时不能默认成功；必须结合 managed 状态和 beforeSnapshot 判断是已经完成、从未存在还是记录损坏。

### R5：取消课程缺少恢复开课状态转换

涉及位置：

- `DiffEngine.compute()`
- `ImportManager.commit()` UPDATE/恢复分支
- `ManagedStatus`

现状：

- managed 行已是 `CANCELLED` 时，相同内容的 `PENDING` 事件可能被判为 `UNCHANGED`；
- 内容变化时虽然可能进入 UPDATE，但更新 managed 行时没有强制恢复 `ACTIVE`。

修复要求：

| managed 状态 | 新输入状态 | Diff 结果 | 执行动作 |
|---|---|---|---|
| ACTIVE | CANCELLED | CANCELLED | DELETE |
| CANCELLED | CANCELLED | UNCHANGED | NOOP |
| CANCELLED | PENDING | MODIFIED 或 RESTORE | 创建/恢复系统事件并写 ACTIVE |
| BROKEN | PENDING | REPAIR 或人工确认 | 根据系统真实状态处理 |
| ACTIVE | PENDING | 按 contentHash | UNCHANGED/UPDATE |

UPDATE、RESTORE 或 REPAIR 成功后必须同时更新：

- `status = ACTIVE`
- `calendarEventId`
- 最终 `contentHash`
- 标题、地点、描述、起止时间和提醒
- `lastSeenBatchId` 与 `updatedAt`

### R6：批次状态必须集中汇总

涉及位置：`ImportManager.recover()` 及各 `recover*()` 函数。

现状：`recoverCreate()` 能将 action 标成 `FAILED`，但外层 `needsReview` 不一定收到结果，batch 仍可能成为 `APPLIED`。

修复要求：

1. 单动作函数返回结构化结果，禁止返回 `Unit` 后由调用方猜测。
2. 执行结束后重新查询该批次全部 action，再集中计算 batch phase。
3. 汇总规则至少覆盖：

| 动作集合 | 正向批次 | 撤销批次 |
|---|---|---|
| 全部 DB_APPLIED | APPLIED | 不适用 |
| 全部 REVERTED | 不适用 | UNDONE |
| 包含 FAILED/REVERT_FAILED | PARTIAL | PARTIAL |
| 仍有 PLANNED/CALENDAR_APPLIED | APPLYING | UNDOING |

4. `errorSummary` 必须包含失败动作数量和错误码摘要。

### 步骤 2：重构正向/逆向恢复状态机

执行：

1. 拆分 APPLYING 与 UNDOING 恢复入口。
2. 提取可重入的单动作 apply/revert 函数。
3. 统一 action 状态转换。
4. 集中汇总 batch phase。
5. 保证恢复过程重复调用结果一致。

完成标准：同一恢复函数连续调用三次，不增加系统事件、不误删事件、不改变已完成结果。

### 步骤 3：实现 operation token

执行：

1. 设计数据库字段及唯一约束。
2. 在 CalendarWriter 写入 token。
3. Gateway 实现按 token 查找。
4. CREATE、撤销 DELETE、恢复流程全部接入查询优先逻辑。
5. 处理查询到 0、1、多条三种情况。

完成标准：在 Calendar 写成功后、Room 写入前模拟进程终止，重启恢复后系统日历中仍只有一条目标事件。

### 步骤 4：修复 DELETE 完整性链路

执行：

1. 正常提交和恢复共用同一个确认删除函数。
2. 删除后核查事件是否仍存在。
3. 确认删除后再更新 managed 和 action。
4. 删除失败保留原映射，进入 PARTIAL。

完成标准：Calendar、managed_event、action、batch 四者最终状态一致。

### 步骤 5：实现取消后恢复开课

执行：

1. 在 DiffEngine 中显式判断 managed 生命周期状态。
2. 实现 CANCELLED → ACTIVE 的 RESTORE 语义。
3. 修复 UPDATE/恢复路径遗漏的 `status=ACTIVE`。
4. 增加取消、恢复、再次取消的循环测试。

完成标准：执行 `PENDING → CANCELLED → PENDING → CANCELLED` 后，每一步系统日历数量和 managed 状态均正确。

## 5. 必须补充的测试矩阵

| 类别 | 场景 | 关键断言 |
|---|---|---|
| 正向 CREATE | Calendar 前中断 | 重启后创建一次 |
| 正向 CREATE | Calendar 后、ID 落库前中断 | 按 token 找回，不重复创建 |
| 正向 UPDATE | Calendar 后、managed 前中断 | 补写 managed，内容一致 |
| 正向 DELETE | 删除前中断 | 恢复后完成删除 |
| 正向 DELETE | 删除后、managed 前中断 | managed 补写 CANCELLED |
| 正向 DELETE | Provider 删除失败 | action FAILED、batch PARTIAL、映射保留 |
| 撤销 CREATE | 删除后、REVERTED 前中断 | 重试不报错、不误删其他事件 |
| 撤销 UPDATE | 恢复 Calendar 后、Room 前中断 | 重试后 beforeSnapshot 完整恢复 |

| 生命周期 | CANCELLED → PENDING | 日历事件恢复，managed=ACTIVE |

- 指定某次 insert/update/delete 失败；
- 在调用成功后抛出模拟进程中断异常；

- 返回重复 token 结果；
- 检查事件是否真实存在；
