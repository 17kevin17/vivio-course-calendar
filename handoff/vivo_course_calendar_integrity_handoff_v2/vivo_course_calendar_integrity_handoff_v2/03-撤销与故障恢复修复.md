# 撤销与故障恢复修复

## 一、动作状态必须驱动重试

撤销时只处理尚未恢复的动作：

```kotlin
if (action.state == REVERTED) continue
```

每个逆操作成功后立即写 `REVERTED`。失败时写 `REVERT_FAILED` 或保留可重试状态，不能无条件标记成功。

## 二、撤销规则

### CREATE

- 日历事件存在：删除并确认结果。
- 已不存在：视为幂等成功。
- 删除 managed_event 前确认该行仍指向本动作创建的事件。

### UPDATE

- 用 beforeSnapshot 更新系统事件。
- 更新失败且事件不存在时，根据产品策略重建或转人工确认。
- 系统成功后再恢复 managed_event 快照。
- 恢复 `lastSeenBatchId`、提醒和状态，而不仅是标题时间。

### DELETE

- 如果动作已保存恢复后的新 ID，不再次创建。
- 首次重建成功后立即保存新 calendarEventId。
- insert 返回 null 时不得把 managed_event 标为 ACTIVE。

## 三、CalendarGateway 增强

```kotlin
interface CalendarGateway {
    fun insertEvent(...): Long?
    fun updateEvent(...): Boolean
    fun deleteEvent(...): Boolean
    fun eventExists(id: Long): Boolean
    fun getEvent(id: Long): CalendarEventSnapshot?
}
```

建议给应用创建的事件写可查询标识，例如应用 URI、批次/动作 token 或 CalendarProvider 支持的自定义字段。必须验证 vivo CalendarProvider 是否保留该字段。

## 四、正常执行的中断窗口

### CREATE

危险窗口：Calendar 插入成功，但 action 仍为 PLANNED。

解决：

- 尽可能在事件中写 action token；恢复时按 token 查找。
- 找到唯一事件则补 calendarEventIdAfter。
- 找不到才安全重试。

### UPDATE

危险窗口：系统事件已更新，但 managed_event 仍为旧快照。

解决：读取系统事件并与 before/after 比较：

- 等于 after：补写 DB。
- 等于 before：重试 UPDATE。
- 两者都不等：NEEDS_REVIEW。

### DELETE

危险窗口：系统事件已删除，managed_event 仍是 ACTIVE。

解决：eventExists=false 时补写取消状态；存在则重试删除。

## 五、recover 接入

当前仅定义 `recover()` 不等于启用。

建议在 Application/首个 ViewModel 的 IO 协程执行一次，并确保：

- 不阻塞主线程。
- 同一进程只执行一次。
- 有运行结果日志，但不记录个人数据。
- UI 可显示“恢复了几条/需要人工处理几条”。

扫描范围至少包括：

- PREPARED 超时；
- APPLYING；
- UNDOING；
- PLANNED 超时动作；
- CALENDAR_APPLIED；
- managed_event 指向不存在的系统事件。
